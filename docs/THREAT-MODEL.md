# Threat model: the guarded write path

Scope: `src/signer-env.ts`, `src/policy.ts`, `src/write.ts`, `src/receipts.ts`, `src/ve-actions.ts`, `src/trove-actions.ts` and `src/sp-actions.ts`, whose fourteen write tools are the only callers (`src/plan.ts`, the trove planner, and the three Stability Pool reads (`sp_status`, `allowance_status`, `plan_sp_deposit`) only read the chain and have no signer; the paid plan routes in `src/app.ts` call only those, and a test fails if `src/app.ts` or any `src/worker*.ts` imports, directly or through another file, a signer or key module). Mezo testnet only (chain 31611).
The six `ve_*`, the three `trove_*` and the five Stability Pool tools (`sp_approve_musd`, `sp_deposit`, `sp_withdraw`, `trove_liquidate`, `approve_revoke`) call `createWriter(...).send({ to, data, value })`. They are registered only when the operator sets `MEZO_WRITE_ENABLE=testnet`. The reads (`ve_status`, `gauge_rewards`, `plan_open`, `plan_top_up`, `plan_repay`, `trove_status`, `sp_status`, `allowance_status`, `plan_sp_deposit` and the older tools) never touch the writer.

## Assets

- The testnet wallet key (in the file named by `MEZO_KEY_FILE`) and what the wallet holds: BTC, MUSD and positions.
- The operator's limits: the env caps, the policy file and the kill file.
- The receipts file, which is also the daily ledger the caps read.

## Attacker

- Mainly the model that drives the tools, for example after a prompt injection from a web page, a tool result or a chat message. It controls every tool argument, and it can call tools many times or several at once.
- A wrong or hostile RPC endpoint (`MEZO_RPC_URL`). It answers the chain id, the simulation, gas, fees, the nonce and the receipt.
- Out of scope: anyone with shell access to the operator's machine, who can read the key file anyway.

## Guards, and the tests that prove them

Tests are in `test/write.test.ts` (W), `test/policy.test.ts` (P), `test/ve.test.ts` (VE), `test/trove.test.ts` (T) and `test/sp.test.ts` (S).

## Not covered

- **An open trove can be liquidated or redeemed against.** `trove_open` is risky because the collateral stays in the trove: a price fall that takes the ratio under 110% lets anyone liquidate it, and a redemption (lowest ratios first) takes debt and collateral at face value. The plan warns when the ratio after the change is under 150% or the system ratio is close to the Recovery Mode line, and reports how much redeemable debt is ahead of the trove, but none of that stops a price move. There is no tool that withdraws collateral or closes the trove. The stored borrow cap (`maxBorrowingCapacity`) only limits later borrowing.
- **Crash window.** A crash after `eth_sendRawTransaction` but before the receipt line is appended loses that line. After a restart, the day's total misses that tx, so the day can go over by up to one per-call cap.
- **Several processes on one receipts file.** Each writer serializes only its own sends. Two processes can both pass the daily cap and reuse a nonce, so run one writer per wallet.
- **The RPC is trusted** for the simulation, the gas estimate, the nonce and the receipt status. A lying RPC can make a reverting call look fine, so gas is lost (within the caps), or it can report a wrong status. It cannot change the chain id the tx is signed for, and the BTC caps bound the fee it quotes.
- **What a call does on chain is not measured.** The caps only see what the entry's decoder reads from the calldata, plus the value and the fee. Later effects are not seen: an allowance that stays open, liquidation, redemption, price moves. Each new allow-list entry needs review; the shipped approve entry pins the spender (the veBTC) and an exact amount.
- **The operator is trusted.** Anyone who can edit the env, the policy file or the receipts file can raise the caps or reset the daily total.
- **The day follows the machine's UTC clock.** A wrong clock shifts the day.
- **An approve that is not used.** If `ve_approve_btc` succeeds and the lock is then refused or fails, an allowance of that exact amount stays open for the veBTC contract until a lock uses it up; `sp_approve_musd` does the same for a deposit that then fails. `allowance_status` finds such an allowance and `approve_revoke` sets it back to 0, but the operator or the model has to call them. In the real runs the lock and the deposit used their approvals up (the allowance was 0 afterwards), so `approve_revoke` has not sent a real transaction: on the real chain it only refused, for lack of an allowance.
- **A vote stands for its epoch.** The voter allows one vote per NFT per epoch, so a vote for a poor pool cannot be changed until the next epoch opens. A vote moves no funds, so the caps do not see it.
- **A pool deposit can lose value and can be stuck.** A liquidation takes MUSD from every deposit in the pool and pays the depositor BTC (in the real run our 10 MUSD lost 0.000232 MUSD and gained 3.2e-9 BTC). The pool refuses every non-zero withdrawal while a trove is under 110%; two troves were still under 110% after our liquidation, so `sp_withdraw` was refused twice and has not sent a real transaction, and the deposit stays until those troves are liquidated, topped up or repaid. The caps count the amount deposited but cannot see any of this.
- **`trove_liquidate` acts on a stranger's position.** The guards check that the trove is active and under the minimum at the block read, that the call simulates, and that the operator allowed risky actions. They cannot tell whether liquidating is wise, and someone else can liquidate the same trove first or top it up between the read and the mined block; the transaction then reverts and costs its gas, which the ledger counts. The tool liquidates one trove and never calls the batch functions.
- **The claim tools have not sent a real transaction.** An epoch's fees can be claimed once the epoch ends (Thursday 00:00 UTC; the first one that matters ends 2026-11-05). Before that the claims were only simulated on the chain (they return 0), and the tools were tested against a fake chain.
- **The public RPC is several nodes behind one URL.** Right after a send, a node may not know the receipt, the block or the new state yet (seen more than once in the real run). The write tools ask for the receipt again for 15 seconds and read the new state at the receipt's block. The checks before a send read the head the node reports, so a lagging node can let a call through that then reverts on chain; the cost is its gas, and the ledger counts it.
- **Fees on the real chain** were first seen on 2026-10-31 (three real transactions, all succeeded): gas price 146 wei, our `maxFeePerGas` 172 wei, gas used 25,540 (approve), 548,254 (`createLock`) and 521,580 (`vote`), 159,924,604 wei in all (about 1.6e-10 BTC). The caps count gas limit x `maxFeePerGas`, a small overcount. The trove run the same day (three more real transactions, all succeeded) used 578,967 (`openTrove`), 371,741 (`addColl`) and 349,620 (`repayMUSD`) gas at the same 146 wei price, 189,847,888 wei in all; that is 80 to 82% of the limit each plan suggests (its estimate times 1.2). The Stability Pool run the same day (three more real transactions, all succeeded) used 46,382 (MUSD `approve`), 132,705 (`provideToSP`) and 414,865 (`liquidate`) gas, 86,716,992 wei in all. A fee spike has not been seen.
