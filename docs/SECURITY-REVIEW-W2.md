# Security review of the code, Wave 2

## Scope

- **Commit reviewed:** `fd086b8` ("docs: shorter build note; commit count"), checked out in its own worktree on branch `w2/r-review`. The fixes below are later commits on that branch.
- **Files:** everything in `src/` (the MCP server, the CLI, the x402 buyer and spend guard, the guarded write path, the policy and receipts ledger, the vote-escrow, trove and Stability Pool tools, the lens and planners, the Worker and its console page), the scripts in `scripts/` that read a key, sign or pay (`deploy.ts`, `swap.ts`, `gate.ts`, `w2-paid.ts`, `mcp-session.ts`, `worker-smoke.ts`, `video/take.ts`, `secret-scan.mjs`, `build-mcp.mjs`), and the parts of the installed libraries our guards rely on: `@x402/core`, `@x402/evm`, `@x402/fetch` and `@x402/hono` 2.28.0 (hooks, route matching, the re-pay path, the reference facilitator's verify) and Hono 4.13.13 (HEAD handling).
- **Not reviewed:** the contracts, the facilitator service itself, and `docs/THREAT-MODEL.md` as a document (it was read only for the cross-check at the end).
- **Method:** a line-by-line reading of the code against eight focus areas: key handling, the spend limits and the x402 spend guard, the write path (simulate, caps, send, receipt), the contract and function allow-list, the pay_and_fetch host allow-list, input checks on every MCP tool argument and Worker route, error messages and logs, the paid `/plan/*` routes, and number and unit handling. Each signing path (an x402 payment and a guarded write) was traced end to end into the library code. For each High and Medium finding a test was written first and run to see it fail, then the smallest fix was made and the test run again. No transaction was sent and no paid call was made: the tests use a mocked RPC and a fake facilitator.

## Severity

- **High:** can sign or pay beyond the stated limits, bypass an allow-list, leak a key, or break the live Worker.
- **Medium:** a guard that fails open in an edge case, a wrong number or status a user would act on, a missing check at a trust boundary, or a test that passes while the feature is broken.
- **Low:** everything else. Listed, not fixed.

## Fixes

Each fix was made after its test was written and seen to fail; the tests pass after the fix.

- **R1 (`289d1f9`):** before its first RPC call, a send now creates a lock file next to the receipts file (the receipts file name plus `.lock`, created only if it does not exist yet, mode 0600) and removes it after the receipt line is written. So only one process at a time can check the caps and send for one receipts file; a second process is refused at once, before any RPC call, with a message that says to try again in a minute. If the receipt line cannot be written, the lock stays, and a process killed during a send leaves it too. A lock that stays is never taken over automatically: like the kill file, it keeps every write off until the operator compares the wallet's latest transaction with the receipts file and deletes the lock. The comment at `write.ts:6` now says "also across processes". Tests in `test/write.test.ts`, under "one writer at a time across processes": "a second writer on the same receipts file is refused while a send is in flight, then sees its line" (afterwards its own send is refused by the per-day cap, which now includes the first writer's line), "a lock left behind keeps writes off before any RPC call, until the operator deletes it" and "a sent tx whose receipt line cannot be written keeps the lock, so no process writes until the operator checks". `docs/THREAT-MODEL.md` was updated to match (the ledger row, the "One send at a time" row and the crash bullet).
- **R2 (`d8ad548`):** `checkUrl` now takes `https://` for every allowed host, and plain `http://` only when the host is `127.0.0.1`, `localhost` or `[::1]`, where no one on the network path can answer in the server's place. The `pay_and_fetch` description says so. Tests: `test/pay.test.ts` "refuses plain http except to this machine, where nobody on the network path can rewrite the 402", and an `http://` URL added to the refused URLs in `test/mcp.test.ts` "reports an unusable url or a host that is not allowed as an error that says nothing was paid" (before the fix, that URL was paid). The test fixtures that used `http://` hosts now use `https://`.
- **R3 (`d157b61`):** `readKeyFile` now looks at the key file's mode after reading it. If any group or other permission bit is set (not on Windows), it prints one warning on stderr that names neither the path nor the key and says to run `chmod 600`. The key still loads: a warning, not a refusal, so setups that create key files with the default mode keep working. The warning goes to stderr because stdout carries the MCP messages. Test: `test/keys.test.ts` "warns, without the path or the key, when other accounts can read the key file, and still loads it". One row ("Key file mode") was added to `docs/THREAT-MODEL.md`.

## Checked and found fine

- **The spend guard cannot be skipped.** The library calls the guard's hook before it creates every payment and aborts on a refusal, so nothing is signed. Only the exact EVM scheme for `eip155:31611` is registered (no version 1 client). The signer handed to the library has no `signTransaction`, so it cannot send a transaction on its own. The EIP-2612 permit is for the exact payment amount. Per-call and per-session limits are counted when a payment is approved and never given back. Redirects are not followed, so a payment header never goes to a second host.
- **The write path runs in a safe order and fails closed:** off unless `MEZO_WRITE_ENABLE=testnet`, then the kill file, the shape of the call, chain id 31611, the caps, an `eth_call` simulation, the gas cap (3,000,000), the caps again with the worst-case gas fee, the kill file again, a local signature with the chain id from the config, the raw send, the receipt and the ledger line. The transaction value and the worst-case fee both count as BTC. A ledger line that cannot be read stops all writes.
- **The contract and function allow-list:** each entry is pinned to one contract and one selector, and its amounts are decoded from the calldata. The argument orders match `src/abis.ts`. There is no transfer entry, and every approve has a fixed spender. A policy file can only tighten the caps, shrink the list or turn the risky flag off, and risky entries need `MEZO_WRITE_RISKY=1`.
- **The host allow-list:** an exact host or host:port, compared without case, no wildcard. A blank or comma-only setting falls back to the default list, never to "any host". A URL with a user name or password is refused.
- **Input checks:** every MCP tool argument has a schema with lengths. The Worker routes parse addresses, tokens, amounts and flags before the 402 is issued, so a bad request never costs the buyer anything. The `/plan/*` bodies have a size limit and unknown fields are dropped.
- **Errors and logs:** the key reader's errors are generic. Nothing logs the environment, a key or a key path. The payments route answers a chain failure with a generic 502. A Worker setting that is wrong is named without its value. The npm bundle carries no key paths (`test/package.test.ts`).
- **The paid `/plan/*` routes:** the price comes from the same parser as the console page, inputs are checked before the 402, and a refused plan is a paid 200 by design.
- **Numbers and units:** MUSD and BTC are 18-decimal amounts handled as bigint on the write and payment paths, and parsed and printed with viem's `parseUnits` and `formatUnits`.
- **Operator scripts:** `scripts/deploy.ts` and `scripts/swap.ts` sign directly; they are run by hand and are not reachable from the MCP server or the Worker. The swap approves exactly the amount it swaps and allows 1% slippage. The scripts that pay use the same buyer and spend guard with tight limits, against a local server or an https URL.

## Cross-check with earlier documents

After the findings above were written, they were compared with `docs/THREAT-MODEL.md` as it was at `fd086b8` and with an internal audit made earlier in this wave (not published), in particular its items on the key file mode and on `npm audit`.

- **R1, known but rated differently.** The threat model listed all three parts as accepted risks: several processes on one receipts file under "Not covered" ("run one writer per wallet"), the crash window ("the day can go over by up to one per-call cap"), and a receipt line that cannot be written (counted "in memory" by that process only). The internal audit called the write path sound, citing the one-at-a-time sends and the daily cap re-read from the receipts file. I rate it High because it lets the wallet spend beyond the stated per-day cap in normal use, not only after a crash: the install guide adds the server to an MCP client (`docs/INSTALL.md:78`), and every client session starts its own server process, so two open sessions on one wallet are two writers, and nothing in the code enforced "one writer per wallet".
- **R2, new.** Neither document mentions the URL scheme. The threat model covers the write path only; the internal audit noted that `pay.ts` does not follow redirects.
- **R3, known, rated higher, same fix.** The internal audit had this in its lowest tier, priority 2 ("cleanup, optimization"), as an item that could be done at once, with the same fix: warn, do not refuse, one test, one threat-model row. I rate it Medium, a missing check at a trust boundary: the key file is where the key enters the code. The threat model's line "anyone with shell access to the operator's machine, who can read the key file anyway" (out of scope) assumes the file is private to the operator's account. A key file with mode 0644 is not: every account on the machine, and every copy or backup of the folder, can read it.
- **R6, known.** The internal audit lists the payment memory that each Worker instance keeps for itself as an open Wave 1 promise, and the README says the same. This review adds what stops a replay across instances (the facilitator's verify).
- **R9, partly known.** The threat model notes that "the day follows the machine's UTC clock" (a wrong clock shifts the day), but not the double spend allowed around midnight.
- **R8, new.** The threat model's "Caps fail closed" row says that a per-call cap above its per-day cap turns writes off. That holds for the environment caps, not after a policy file lowers a per-day cap. No limit can be passed either way, since the write check applies both caps, so it stays Low.
- **R4, R5, R7, R10 and R11, new.** Neither document mentions them.
- **R12, known; now traced.** The internal audit found the same nine advisories, listed the parent of each, noted that the shipped bundle `dist/mcp.js` contains code from zod, `@x402` and fast-uri, and left open whether any advisory is reachable. Traced here against `@x402` 2.28.0 and the MCP SDK as installed:
  - zod 3.25.76 comes with `@x402/core`, `@x402/evm` and `@x402/extensions`; `@x402/fetch` and `@x402/hono` are flagged only through `@x402/core`. The advisory (GHSA-mrhx-c7xc-m3w5, zod before 4.6.6) is about validating oversized collections that have a size limit. On the Worker, the payment header a caller sends is read with `JSON.parse`, not with zod. The only zod 3 schemas that run check the facilitator's verify, settle and supported answers, and none of them has a size limit. The schemas with a size limit (the payment payload and the 402 answer) are exported but not called by the `@x402` code this project runs, on the Worker or in the buyer. Of the `@x402/extensions` code, only the EIP-2612 declaration is used, and it does not call zod. The MCP SDK and this code use zod 4.6.7, which has the fix.
  - body-parser comes with express in the MCP SDK's HTTP transport; the server uses only the stdio transport (`src/mcp.ts`).
  - fast-uri comes with ajv; the MCP SDK's server uses ajv only to check the answer to a form elicitation, and this server never asks for one.
  - follow-redirects is inside `solc`, the compiler used to build the contracts; it is not part of the server, the Worker or the bundle.

  So I rate it Low. No package was upgraded.

## Limits of this review

- One reviewer, one pass: a static reading plus unit tests against mocks. There was no live transaction, no paid call, no fuzzing and no load test.
- The contracts and the facilitator service were not reviewed. What the facilitator does comes from reading the reference code in `@x402` 2.28.0, not from tests against the live facilitator.
- The x402 and Hono behaviour was read from the installed versions; an upgrade can change it.
- The R1 lock was tested on a local Linux disk only. It relies on creating a file only if it does not exist yet, which some network file systems do not guarantee; Windows was not tested.
- The dependency trace for R12 is a reading of the installed build output, not a test with oversized input.
- The review was not fully blind: the instructions for this review named one earlier finding (the key file mode) in advance, and one search printed five lines of `docs/THREAT-MODEL.md` before these findings were written.
